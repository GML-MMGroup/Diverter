# Decision Rules

Apply these examples only after the core Eligibility rules. An implicit `Yes` requires one bounded Child Lane, one distinct useful Root Lane, material benefit, non-duplication, and safe ownership.

| Task shape | Decision | Child Lane | Root Lane |
| --- | --- | --- | --- |
| Explicit delegation request | Yes when clear and safe | requested bounded specialist work | any remaining orchestration or task outcome; the implicit benefit threshold is bypassed |
| Code path plus official docs | Yes | verify the documented API contract | trace the implementation and frame the decision |
| Focused skill ownership plus separate audit | Yes | non-duplicative Supporting Child audit | focused skill keeps its core workflow |
| Known regression plus bounded test work | Yes | design or implement the targeted proof | map the behavior boundary and integrate results |
| Research with two deliverables | Yes | gather one bounded evidence set | develop the synthesis structure or another distinct deliverable |
| Domain-neutral mutable artifact with disjoint ownership | Yes | edit one declared artifact or section | progress another disjoint artifact or section |
| Specialist offload with no useful Root work | No implicitly | specialist could work | Root would only wait or supervise |
| Same-scope follow-up with a reusable child | Reuse | continue the existing Child Lane | integrate or advance the related Root Lane |
| Materially different follow-up | Maybe new child | new bounded deliverable | distinct Root Lane still required implicitly |
| Focused skill with duplicate helper | No | duplicates the skill | no independent benefit |
| Trivial or wording-only change | No | too small | no distinct useful lane |
| Immediate critical-path fact | No | one blocking lookup | no independent progress before the answer |
| Tightly coupled or overlapping writes | No in parallel | conflicting ownership | serialize or keep in Root |
| Ambiguous request | No yet | scope unknown | clarify first |
| Explicit opt-out | No | none | Root only |
| Delegated-subagent handoff | No | current handoff already is the Child Lane | parent owns orchestration |
| Native Proactive Delegation active | No | native policy owns children | continue under native orchestration |
| Vague risk language about security, tests, performance, or release | No yet | no concrete boundary | clarify the artifact or deliverable |

Practical tie-breakers:

- A specialist title alone does not create a Child Lane.
- Read-only work is safer, but still needs a useful Root Lane.
- Default to one child. Add another only for another necessary, independent deliverable.
- A missing role is removed; Root covers that capability without role substitution.
- A write-capable lane must declare Write Ownership. Serialize overlap.
- Never count “I will wait and synthesize” as substantive Root progress.
